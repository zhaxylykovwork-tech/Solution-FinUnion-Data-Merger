# BIAN: референсные границы

Используется зафиксированный [BIAN release 13](https://github.com/bian-official/public/tree/main/release13.0.0/semantic-apis/oas3/yamls). 10 сопоставлений ниже — архитектурная интерпретация. Не каждое понятие равно одному Service Domain: карта бывает дебетовой/кредитной, договор бывает разных продуктов. Вводный термин Party Data Management уточнён до имени области выбранной версии.

| Сущность | Область BIAN / первичный источник | Локальная интерпретация, владелец и устранение пересечений FU/RB |
|---|---|---|
| E01 Customer (+ E02) | [Party Reference Data Directory](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/PartyReferenceDataDirectory.yaml) | Сторона и справочные атрибуты имеют общий словарь и crosswalk; Customer Owner отвечает за золотую запись; дубли двух CRM разбираются Hub. Основа Customer 360 |
| E03 Agreement | [Customer Agreement](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CustomerAgreement.yaml), [Sales Product Agreement](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/SalesProductAgreement.yaml) | Общие отношения и конкретный продуктовый договор различаются. В нашей E03 моделируется продуктовый договор; профильный owner утверждает условия, Hub не переписывает договоры |
| E05 Account | [Current Account](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CurrentAccount.yaml), [Corporate Current Account](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CorporateCurrentAccount.yaml) | Единый смысл счёта и статусов с разделением retail/SME. Core владеет счётом, два Core объединяются в аналитике без смешения ledger |
| E06 Card | [Credit Card](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CreditCard.yaml), [Card Authorization](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CardAuthorization.yaml) | Карточный продукт и авторизация различаются. Дебетовая карта не объявляется кредитной: используем общие карточные границы и отдельный тип продукта. Cards owner сопоставляет статусы FU/RB |
| E07 Loan | [Consumer Loan](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/ConsumerLoan.yaml), [Corporate Loan](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CorporateLoan.yaml) | Отдельны retail и corporate обязательства; Loans owner управляет графиком, переносом и риском. Основа Loan Portfolio |
| E08 Posting | [Position Keeping](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/PositionKeeping.yaml) | Проводки/позиции отделены от команды оплатить. Учетный owner/Core сверяет обе ledger-модели. Основа Ledger Daily |
| E09 Payment | [Payment Execution](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/PaymentExecution.yaml) | Единые статусы исполнения и external reference; payment owner предотвращает повторную отправку при миграции. Поручение не дублирует Posting |
| E10 Product (+ E11) | [Product Directory](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/ProductDirectory.yaml) | Общие codes/version и сопоставление RB→FU с сохранением старого тарифа в договоре; продуктовый комитет публикует мастер-справочник. Основа Product Catalogue |
| E12 Branch | [Location Data Management](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/LocationDataManagement.yaml) | Отделение — локальный вид location, общая нумерация с bank_id; владелец сети подтверждает реорганизации |
| E14 Case | [Customer Case Management](https://github.com/bian-official/public/blob/main/release13.0.0/semantic-apis/oas3/yamls/CustomerCaseManagement.yaml) | Единый жизненный цикл обслуживания, история двух CRM; контактный центр владеет статусом и сроками, не банковскими проводками |

E04 наследует границы договоров/сторон, E13 — локальный классификатор Customer Owner, E15 — управление правовым основанием, E16 — документный контур. Для них не выдумывается тождество произвольной BIAN-области.

Практический результат: FU active и RB open маппятся в канонический статус с сохранением оригинала; названия «клиент», «держатель», «плательщик» больше не взаимозаменяемы. Матрица мастеров использует эти же границы. Два Core не становятся двумя владельцами одной записи после cutover. Центральная команда предоставляет стандарты/инфраструктуру, бизнес-домены отвечают за контракты своих [data products](../Task3/data-products.md); полноценный Data Mesh для этого не требуется.
